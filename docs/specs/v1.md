# Starchive v1 · 本地星标资料库与 Agent 选型对话

## Problem Statement

我记得给一个仓库加过星，也记得当时想用它解决什么问题，却想不起它的名字。开始一个新项目时，我想直接描述效果，看看自己收藏的哪些仓库值得用、各自适合做哪一部分。现在我得在星标列表、多个 README 和聊天窗口之间来回切换，隔天还得重新整理比较依据。

## Solution

把 GitHub 星标同步到本机。在桌面端，左侧筛选资料库，中间浏览列表或仓库详情，右侧始终可以和自己配置的本地 Agent 讨论需求。Agent 优先从我的星标库找候选，说明每个候选的用途、依据和资料缺口。我可以边读 README 边追问，也可以主动扩展到 GitHub 搜索。命令行和桌面端共享同一份资料。

## User Stories

1. 作为 GitHub 用户，我希望一次同步取回各页星标，以便在本机浏览完整收藏。
2. 作为回访用户，我希望看到最近一次成功同步的时间和本次同步的结果，以便判断资料的新鲜度。
3. 作为离线用户，我希望能浏览、检索和编辑已保存的资料，以便网络中断时继续整理。
4. 作为收藏者，我希望通过名称、描述或自己的笔记找回仓库，以便只记得用途时也能找到它。
5. 作为收藏者，我希望按语言和标签筛选，并为仓库写下收藏理由，以便下次快速识别它。
6. 作为长期用户，我希望仓库改名后仍能找到原来的笔记与标签，以便保留自己的整理成果。
7. 作为终端用户，我希望用独立的 `starchive` 命令同步、搜索、查看及整理仓库，以便回到桌面端能接着使用同一份数据。
8. 作为项目发起者，我希望在右侧直接描述想实现的效果，以便从整个星标库寻找候选。
9. 作为选型者，我希望看到每个推荐对应哪项需求、依据来自哪份资料，以及哪些能力仍待确认，以便判断是否值得深入阅读。
10. 作为阅读者，我希望点击候选后在中间查看详情，右侧保留对话，以便核对依据后继续追问。
11. 作为选型者，我希望显式把一个或多个仓库加入对话并看见已选项，以便准确指明比较对象。
12. 作为有多个项目的用户，我希望新建、切换和恢复本地对话，以便隔天继续某次选型，找回当时的候选和讨论。
13. 作为选型者，我希望在收藏不足时看见候选缺了什么，并能点击「扩展到 GitHub 搜索」，以便沿用当前需求发现新项目。
14. 作为用户，我希望每次新的 GitHub 搜索都由我触发，返回的候选可在本轮对话之外继续追问，以便控制何时对外查询。
15. 作为收藏者，我希望看清候选是「已星标」还是「尚未星标」，并能在 GitHub 打开仓库，以便加星后通过下次同步纳入资料库。
16. 作为本地 Agent 用户，我希望选择已安装的 Agent 并了解其推理可能联网，以便沿用我的工具和模型配置。
17. 作为私有仓库用户，我希望自行选择是否将私有资料和个人笔记加入对话，以便控制提供给 Agent 的内容。
18. 作为用户，我希望同步或 Agent 调用失败时看到可操作的原因，并保留已保存的资料与对话，以便恢复后重试。

## Implementation Decisions

- 使用 Cargo workspace，成员为 core、cli、desktop，另设 frontend。核心采用 Rust、异步 sqlx 和 SQLite；独立二进制 `starchive` 使用 clap；桌面端使用 Tauri 2.x 和 TypeScript。项目采用 MIT 许可证。
- core 持有同步、检索、整理、会话和 Agent 调用的业务规则。CLI 负责参数、输出与退出状态，Tauri 为前端转发操作及进度。两个入口共享本地数据库、迁移和同步协调机制。
- 以稳定的 GitHub 仓库 ID 关联仓库资料、星标状态、标签和笔记。同步覆盖远端元数据，保留个人整理内容。建议仅在完整分页成功后确认已取消星标的条目；保留其笔记与标签，可通过筛选找回。失败或并发重试时，已完成的收藏视图仍可用。
- 应用资料及对话历史保存在本机。对话记录保存候选引用和用户主动加入的资料范围，使重启后可以恢复。浏览详情与加入对话是两个独立动作；右侧显示当前会话与显式加入的仓库。
- Agent 适配层负责调用用户选择的本地可执行程序，如 pi、Codex 或 Claude Code。具体适配器可依据各工具实际支持的非交互接口实现。检索星标、读取已授权资料和引用候选都经过 core；私有仓库资料和个人笔记需要用户主动选择，检索摘要和后续追问也沿用这一范围。
- 星标推荐默认使用本地资料。每次点击「扩展到 GitHub 搜索」允许执行一次面向当前需求的外部搜索；后续比较复用已返回的候选。再次发起搜索需要新的点击。Agent 的模型推理与 GitHub 搜索分别处理，外部搜索条件只需包含面向公开仓库的查找需求。
- GitHub 访问采用读取星标和所选仓库资料所需的权限。候选提供「在 GitHub 打开」，加星操作在 GitHub 完成。外部候选可保存在本地会话中，资料库的星标状态由同步结果决定。

## Testing Decisions

- 建议以 core 的公开用例为主要自动化测试入口，复用真实临时 SQLite，控制 GitHub 分页、失败响应和 Agent 输入输出。断言用户能读到的数据、能执行的操作及跨边界传出的内容。当前仓库尚无可沿用的应用测试或原型。
- 同步验收覆盖多页、改名、取消星标、分页中断及重试。让 CLI 和 GUI 同时请求同步，验证条目唯一、个人笔记完整，已保存资料仍可读；再从另一入口读回刚刚编辑的内容。
- 对话验收以「我想为桌面应用增加中文离线搜索」为样例。从星标找到候选并给出可核对的资料依据，资料不足时显示缺口；新建另一段对话，再重启并恢复原对话，仍能继续比较原候选。使用可控的 Agent 响应验证流程，不匹配固定生成文案。
- 记录向 Agent 提供的资料和面向 GitHub 的搜索请求。验证默认输入、显式加入私有资料、一次授权一次搜索、复用候选追问及再次授权。用混合公私有数据和带个人笔记的仓库检验默认可见范围。
- 桌面端验收中点击推荐、浏览详情、加入两个仓库并切换会话，核对中间详情、右侧历史和上下文标签。发布验收再用实际支持的本地 Agent 走通一次推荐与追问，并验证找不到可执行程序时的恢复提示。

## Out of Scope

应用数据的云端存储与跨设备同步、在应用内修改 GitHub 星标、自建模型托管服务，以及由 Agent 自动发起连续的 GitHub 搜索。

## Further Notes

首版应能演示一条完整路径：同步自己的星标，描述项目需求，在资料库内找到并核对候选，按需扩展到 GitHub，在 GitHub 加星，再同步并于次日恢复讨论。本地资料的离线浏览与搜索独立于 Agent 的可用性；离线对话能力取决于所选 Agent 的推理后端。具体前端组件库、首发 Agent 适配器清单和命令参数可在实现时确定。
